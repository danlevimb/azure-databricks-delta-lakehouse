# Sample Data

This folder documents the sample data strategy used by the `azure-databricks-delta-lakehouse` project.

The project does not require manually committed CSV files to run. Instead, the sample source data is generated by a Databricks notebook and written directly to the ADLS Gen2 `landing` container.

### 1. Purpose

The sample data was designed to support a complete Azure Databricks Delta Lakehouse demonstration.

The dataset is intentionally small, controlled, and scenario-rich.

It supports the following patterns:

- Batch-style source data generation
- Bronze ingestion
- Silver data quality validation
- Rejected records handling
- Schema evolution
- Gold dimensional modeling
- SCD Type 2 customer history
- Fact table construction
- Delta MERGE / upsert
- Delta time travel validation
- Final data quality validation

### 2. Source Data Generation

Sample data is generated by the notebook:

```text
notebooks/01_generate_sample_data.py
```

The notebook writes CSV files to the ADLS Gen2 `landing` container.

Target path:

```text
landing/source_data/
```

The source data is organized into batches.

```text
landing/source_data/
  batch_001/
    customers.csv
    products.csv
    orders.csv
    order_items.csv

  batch_002/
    customers.csv
    orders.csv
    order_items.csv

  batch_003_schema_evolution/
    customers.csv
    orders.csv
    order_items.csv
```

### 3. Why CSV Files Are Not Committed

The generated CSV files are not committed to this repository.

This is intentional.

The repository stores:

```text
Notebook logic
Documentation
Architecture notes
Evidence
Execution guidance
```

The ADLS Gen2 environment stores:

```text
Generated source files
Bronze Delta tables
Silver Delta tables
Gold Delta tables
Validation reports
```

This keeps the repository lightweight and avoids committing generated runtime artifacts.

### 4. Source Entities

The generated dataset includes four source entities.

| Entity | Description |
|---|---|
| `customers` | Customer master data |
| `products` | Product reference data |
| `orders` | Order header data |
| `order_items` | Order line-level data |

These entities are generated as CSV files and then processed into Delta Lake tables.

### 5. Batch Design

The sample data is divided into three batches.

| Batch | Purpose |
|---|---|
| `batch_001` | Initial baseline dataset |
| `batch_002` | Incremental updates, new records, and invalid references |
| `batch_003_schema_evolution` | Schema evolution and additional validation scenarios |

### 11. Schema Evolution Scenario

The `customers` source introduces a new column in batch 003:

```text
loyalty_tier
```

This column is intentionally absent from earlier batches.

Expected behavior by layer:

| Layer | Expected handling |
|---|---|
| Landing | Stores source file as generated |
| Bronze | Preserves the new column |
| Silver | Adds missing column for earlier records and keeps schema consistent |
| Gold | Includes `loyalty_tier` in customer SCD2 tracking |


The time travel notebook compares the product dimension before and after MERGE.

Expected result:

```text

After MERGE  → 5 products
```

