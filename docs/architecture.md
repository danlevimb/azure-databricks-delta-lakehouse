# Architecture

This document describes the architecture of the `azure-databricks-delta-lakehouse` project.

The project implements a cost-aware Azure Databricks Delta Lakehouse using PySpark, ADLS Gen2, Delta Lake, and a Bronze/Silver/Gold data architecture.

### 1. Architecture Objective

The objective of this architecture is to demonstrate how raw source files can be transformed into validated, versioned, and analytics-ready Delta tables using Azure Databricks.

The project focuses on practical Lakehouse engineering patterns:

- Source data landing
- Bronze raw Delta tables
- Silver clean and rejected Delta tables
- Gold dimensional and fact model
- SCD Type 2 dimensional history
- Delta MERGE / upsert
- Delta time travel
- Data quality validation
- Git-integrated notebook execution
- Secure credential handling
- Cost-aware compute usage

The architecture is intentionally scoped as a portfolio-ready MVP, not as a full production platform.

### 2. High-Level Architecture

The project uses Azure Databricks as the processing layer and Azure Data Lake Storage Gen2 as the Lakehouse storage layer.

```text
Source CSV files
      ↓
ADLS Gen2 landing container
      ↓
Azure Databricks / PySpark notebooks
      ↓
Bronze Delta tables
      ↓
Silver clean and rejected Delta tables
      ↓
Gold dimensions, facts, and summaries
      ↓
Delta MERGE, time travel, and validation reporting
```

#### Main Components

| Component | Role |
|---|---|
| Azure Databricks | Executes PySpark notebooks and Delta Lake operations |
| ADLS Gen2 | Stores landing files and Delta tables |
| Delta Lake | Provides transactional table storage and versioning |
| PySpark | Implements transformations, joins, validations, and aggregations |
| Databricks Git Folder | Connects Databricks notebooks to the GitHub repository |
| Databricks Secret Scope | Supports secure credential handling |
| GitHub | Public source control and portfolio repository |

### 3. Azure Resource Strategy

The project uses a clean Azure setup instead of reusing infrastructure from previous portfolio projects.

This decision keeps the Databricks Lakehouse project isolated from earlier Azure Data Factory and event-driven pipeline work.

#### Resource Separation Strategy

| Resource Type | Strategy |
|---|---|
| Resource Group | New project-specific resource group |
| Storage Account | New project-specific ADLS Gen2 storage account |
| Databricks Workspace | New Databricks workspace for this project |
| Containers | New clean containers for Lakehouse layers |
| ADF resources | Not reused or modified |
| Event Hubs | Not used in this project |
| Previous project resources | Kept separate or deleted if no longer needed |

#### Rationale

A clean resource setup provides:

- Clear project boundaries
- Cleaner evidence capture
- Lower risk of affecting previous projects
- Simpler cost tracking
- Easier explanation in documentation
- Better repository-to-infrastructure alignment

### 4. Storage Architecture

The project uses Azure Data Lake Storage Gen2 containers to separate Lakehouse zones.

```text
ADLS Gen2 Storage Account
  ├── landing
  ├── bronze
  ├── silver
  ├── gold
  ├── rejected
  ├── metadata
  └── evidence
```

#### Container Responsibilities

| Container | Purpose |
|---|---|
| `landing` | Source CSV files generated by the project |
| `bronze` | Raw Delta tables with technical metadata |
| `silver` | Clean Delta tables and rejected records |
| `gold` | Analytical dimensions, facts, and summaries |
| `rejected` | Reserved for rejected data patterns or future expansion |

### 5. Data Flow Architecture

The project follows a layered Lakehouse data flow.

```text
landing/source_data
      ↓
bronze/delta_lakehouse
      ↓
silver/delta_lakehouse
      ↓
gold/delta_lakehouse
      ↓
metadata/delta_lakehouse/validation_reports
```

#### Landing Layer

The landing layer stores controlled source CSV files.

```text
landing/source_data/
  batch_001/
  batch_002/
  batch_003_schema_evolution/
```

The landing layer represents the raw source file arrival area.

#### Bronze Layer

The Bronze layer stores raw source records as Delta tables.

Bronze tables preserve source data and add technical metadata.

```text
bronze/delta_lakehouse/bronze_customers
bronze/delta_lakehouse/bronze_products
bronze/delta_lakehouse/bronze_orders
bronze/delta_lakehouse/bronze_order_items
```

#### Silver Layer

The Silver layer stores typed, cleaned, and validated data.

It also stores rejected records in a normalized rejected-records table.

```text
silver/delta_lakehouse/silver_customers_clean
silver/delta_lakehouse/silver_products_clean
silver/delta_lakehouse/silver_orders_clean
silver/delta_lakehouse/silver_order_items_clean
silver/delta_lakehouse/silver_rejected_records
```

#### Gold Layer

The Gold layer stores analytics-ready dimensions, facts, and summaries.

```text
gold/delta_lakehouse/gold_dim_customer_scd2
gold/delta_lakehouse/gold_dim_product
gold/delta_lakehouse/gold_fact_orders
gold/delta_lakehouse/gold_daily_sales_summary
gold/delta_lakehouse/gold_customer_sales_summary
```

#### Metadata Layer

The metadata layer stores validation reports generated by the final validation notebook.

```text
metadata/delta_lakehouse/validation_reports/
```

### 6. Processing Architecture

Processing is implemented using Databricks notebooks written in Python and PySpark.

The notebooks are executed in sequence.

```text
00_environment_setup
01_generate_sample_data
02_bronze_ingestion
03_silver_transformations
04_gold_dimensions
05_gold_facts_and_aggregates
06_delta_merge_upsert_demo
07_time_travel_validation
08_data_quality_validation
```

#### Processing Pattern

The architecture uses path-based Delta tables.

This means the tables are stored and accessed through ADLS Gen2 paths instead of relying on a production catalog design.

Example path pattern:

```text
abfss://gold@<storage-account>.dfs.core.windows.net/delta_lakehouse/gold_fact_orders
```

This approach keeps the MVP focused on PySpark, Delta Lake, and Lakehouse data engineering patterns.

### 8. Logical Lakehouse Model

The project follows a Bronze/Silver/Gold architecture.

#### Bronze

Bronze stores data close to the source format.

Main responsibilities:

- Preserve source records
- Add ingestion metadata
- Preserve schema changes where possible
- Keep invalid business records for traceability
- Write data as Delta tables

Bronze does not enforce business validity.

#### Silver

Silver creates trusted datasets.

Main responsibilities:

- Cast data types
- Standardize strings
- Apply required-field checks
- Apply business validation rules
- Apply referential validation
- Separate rejected records
- Write clean and rejected records as Delta tables

Silver is the quality gate of the Lakehouse.

#### Gold

Gold creates analytics-ready tables.

Main responsibilities:

- Build dimensions
- Preserve customer history through SCD Type 2
- Build fact tables
- Apply latest-state logic for updated orders
- Generate analytical summaries
- Demonstrate Delta MERGE and time travel
- Provide validated outputs for downstream consumption

Gold is the serving layer for analytical use cases.

### 9. Delta Table Strategy

The project uses Delta Lake for all Bronze, Silver, Gold, and metadata outputs.

#### Delta Capabilities Demonstrated

| Delta Capability | Demonstrated In |
|---|---|
| Delta writes | Bronze, Silver, Gold, Metadata |
| Transaction log | All Delta outputs |
| Schema handling | Bronze and Silver |
| MERGE / upsert | `gold_dim_product` |
| Time travel | `gold_dim_product` version comparison |
| History inspection | Delta table history validations |
| Partitioning | `gold_fact_orders` and `gold_daily_sales_summary` |

#### Path-Based Delta Tables

The project uses path-based Delta tables.

Example:

```python
spark.read.format("delta").load(gold_fact_orders_path)
```

This avoids adding catalog and governance complexity to the MVP.

### 10. Data Quality Architecture

Data quality is implemented in the Silver layer and validated again in the final validation notebook.

#### Silver Quality Controls

The Silver layer applies:

- Required field validation
- Type casting
- Allowed value validation
- Referential validation
- Business-rule validation
- Rejected record capture

#### Rejected Records Pattern

Invalid records are written to:

```text
silver_rejected_records
```

Each rejected record includes:

- Entity name
- Rejection reason
- Ingestion batch ID
- Source file path
- Raw record hash
- Rejection timestamp
- JSON representation of the rejected row

This pattern creates a traceable and auditable error handling approach.

The product dimension is implemented as a current-state dimension.

Table:

These tables demonstrate analytical serving patterns over curated Gold data.

### 12. SCD Type 2 Architecture

The SCD Type 2 logic is implemented in the Gold customer dimension.

#### Change Detection

The project calculates a hash from tracked customer attributes.

If the current hash differs from the previous customer version hash, a new version is created.

Tracked attributes:

```text
customer_name
email
city
state
customer_segment
loyalty_tier
```

#### Historical Versioning

Each customer version has:

```text
effective_start_ts
effective_end_ts
is_current
```

The current version has:

```text
effective_end_ts = null
is_current = true
```

Closed historical versions have:

```text
effective_end_ts populated
is_current = false
```

#### As-Of Join

The Gold fact table joins orders to the customer dimension using the order timestamp.

Conceptually:

```text
order_ts >= effective_start_ts
and order_ts < effective_end_ts
```

For current records:

```text
effective_end_ts is null
```

This ensures that each order is linked to the customer version that was valid when the order occurred.

### 13. MERGE / Upsert Architecture

The project demonstrates Delta MERGE on the product dimension.

Target table:

```text
gold_dim_product
```

Source changes:

```text
PROD-002 → updated product price
PROD-005 → new product
```

Expected behavior:

```text
Existing product → update
New product      → insert
```

This demonstrates a common incremental data engineering pattern.

#### MERGE Validation

The project validates:

- Product count after MERGE
- Distinct product count after MERGE
- Updated product value for `PROD-002`
- Inserted product `PROD-005`
- Delta history contains a `MERGE` operation

### 14. Time Travel Architecture

Delta time travel is demonstrated using the product dimension.

The project compares versions before and after the MERGE operation.

Expected comparison:

```text
Before MERGE → 4 products
After MERGE  → 5 products
```

The validation also confirms:

```text
PROD-002 price before MERGE → 35.00
PROD-002 price after MERGE  → 38.00
PROD-005 before MERGE       → not present
PROD-005 after MERGE        → present
```

This shows how Delta table versions can support validation, auditing, and debugging.

### 17. Security Architecture

The project avoids storing credentials inside notebooks.

#### Secret Handling

ADLS Gen2 access is configured through:

```text
Databricks-backed secret scope
Compute-level Spark configuration
```

The repository does not commit:

```text
Storage account keys
Connection strings
Personal access tokens
Plaintext credentials
```

#### GitHub Secret Protection

GitHub push protection was used during development to prevent accidental secret exposure.

If a secret is exposed during development, the expected remediation is:

```text
1. Rotate the secret.
2. Remove the secret from files.
3. Remove the secret from local commit history.
4. Push only sanitized commits.
```

### 18. Cost Architecture

The architecture was designed to control Azure costs.

Cost-control decisions include:

- Project-specific resource group
- Dedicated storage account for this project
- Small single-node Databricks Personal Compute
- Auto-termination enabled
- Manual compute termination after work sessions
- No SQL Warehouse for MVP
- No pools for MVP
- No scheduled jobs for MVP
- No streaming workloads
- Small sample datasets
- Event Hubs not used in this project

The project accepts compute startup latency as a trade-off for lower idle cost.

### 19. Out-of-Scope Architecture Items

The following items are intentionally out of scope for the MVP:

- Unity Catalog governance design
- Production-grade access control model
- Azure Key Vault-backed secret scope
- CI/CD deployment pipeline
- Databricks Jobs orchestration
- Delta Live Tables / Lakeflow Declarative Pipelines
- Streaming ingestion
- Production monitoring and alerting
- Data cataloging and lineage tooling
- Power BI or external semantic model

These items are valid future improvements but are not required for the current MVP.

This architecture demonstrates a practical Azure Databricks Delta Lakehouse implementation.

- Store raw data in a landing zone
- Convert source files into Bronze Delta tables
- Apply Silver data quality rules
- Capture rejected records
- Build Gold analytical tables
- Preserve customer history with SCD Type 2
- Build order-level fact data
