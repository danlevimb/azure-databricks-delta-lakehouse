# Known Limitations

This document describes the known limitations of the `azure-databricks-delta-lakehouse` project.

The project is intentionally scoped as a portfolio-ready MVP focused on Azure Databricks, PySpark, Delta Lake, Bronze/Silver/Gold processing, SCD Type 2, MERGE, time travel, and data quality validation.

It is not intended to represent a fully productionized enterprise Lakehouse platform.

### 1. Purpose of This Document

The purpose of this document is to clearly explain the boundaries of the current implementation.

A strong portfolio project should not only show what was built.

It should also explain what was intentionally left out, why those decisions were made, and how the project could evolve in the future.

This document helps clarify:

- MVP scope
- Technical boundaries
- Cost-aware decisions
- Non-production assumptions
- Future improvement opportunities

### 2. MVP Scope

This project focuses on core Lakehouse engineering capabilities.

In scope:

- Azure Databricks workspace usage
- PySpark notebooks
- ADLS Gen2 path-based storage
- Delta Lake tables
- Bronze/Silver/Gold architecture
- Controlled sample data generation
- Data quality validation
- Rejected record handling
- SCD Type 2 customer dimension
- Gold fact and summary tables
- Delta MERGE / upsert
- Delta time travel validation
- Final validation report
- GitHub and Databricks Git Folder integration
- Secure secret handling through Databricks configuration
- Cost-aware development practices

Out of scope:

- Full production orchestration
- Enterprise governance
- CI/CD
- Streaming
- Unity Catalog design
- Production monitoring
- External BI semantic modeling
- Large-scale performance tuning

### 3. Sample Data Limitation

The project uses controlled sample data generated by a notebook.

Notebook:

```text
01_generate_sample_data
```

The dataset is intentionally small.

This makes it easier to:

- Understand the data
- Validate expected outputs
- Demonstrate transformations
- Capture evidence
- Control cost
- Keep the project reproducible

#### Limitation

The project does not ingest data from a live operational system.

It does not connect to:

```text
SQL Server
REST APIs
ERP systems
CRM systems
Message queues
Streaming sources
Production file drops
```

#### Rationale

The project focuses on Databricks and Delta Lake transformation patterns, not source system connectivity.

Previous portfolio projects already demonstrate ingestion and orchestration patterns.

### 4. Batch Processing Limitation

This project uses batch-style processing.

The notebooks are executed in sequence.

```text
Landing → Bronze → Silver → Gold → Validation
```

#### Limitation

The project does not implement streaming ingestion or real-time processing.

It does not use:

```text
Structured Streaming
Auto Loader
Event Hubs
Kafka
Streaming checkpoints
Continuous processing
```

#### Rationale

Streaming is intentionally excluded to keep this MVP focused on Lakehouse modeling, Delta tables, SCD2, MERGE, and validation.

Streaming can be added as a future enhancement.

### 5. Manual Execution Limitation

The project notebooks are executed manually from the Databricks Git Folder.

#### Limitation

The project does not use Databricks Jobs for production-style orchestration.

It does not include:

```text
Scheduled workflows
Job clusters
Task dependencies
Retry policies
Operational alerting
Job run monitoring
Production orchestration
```

#### Rationale

Manual notebook execution is acceptable for a portfolio MVP.

The goal is to demonstrate technical implementation patterns before adding orchestration complexity.

### 6. No CI/CD Pipeline

The project does not include a CI/CD deployment pipeline.

#### Limitation

The project does not implement:

```text
GitHub Actions
Azure DevOps pipelines
Databricks Asset Bundles
Automated notebook deployment
Automated test execution on pull request
Promotion across dev/test/prod environments
```

#### Rationale

CI/CD is outside the current MVP scope.

The project currently prioritizes clear implementation, documentation, evidence, and interview defensibility.

### 7. Unity Catalog Limitation

The project uses path-based Delta tables.

Example:

```text
abfss://gold@<storage-account>.dfs.core.windows.net/delta_lakehouse/gold_fact_orders
```

#### Limitation

The project does not implement a Unity Catalog governance model.

It does not include:

```text
Catalog design
Schema design
Managed tables
External locations
Storage credentials
Fine-grained grants
Lineage configuration
Table ownership model
Data governance policies
```

#### Rationale

Unity Catalog is a valuable production capability, but it would expand the MVP into governance architecture.

This project intentionally focuses on PySpark, Delta Lake, Bronze/Silver/Gold, SCD2, MERGE, and validation.

### 8. Secret Management Limitation

The project avoids committing secrets to GitHub.

ADLS Gen2 access is configured using:

```text
Databricks-backed secret scope
Compute-level Spark configuration
```

#### Limitation

The project does not use Azure Key Vault-backed secret scopes.

It also does not implement a full production identity model using service principals, managed identities, external locations, or Unity Catalog governance.

#### Rationale

The implemented approach keeps secrets out of notebooks and out of GitHub while keeping the MVP simple.

A Key Vault-backed or Unity Catalog-based approach can be added later.

### 9. Access Control Limitation

The project does not implement production-grade access control.

#### Limitation

The project does not define:

```text
User groups
Role-based permissions
Catalog privileges
Table-level grants
Column-level security
Row-level security
Data masking
Production access policies
```

#### Rationale

The project is a single-developer portfolio MVP.

Access control is acknowledged as important, but it is not required to demonstrate the core Databricks Lakehouse patterns in this phase.

### 10. Data Volume Limitation

The dataset is intentionally small.

#### Limitation

The project does not demonstrate high-scale performance behavior.

It does not test:

```text
Millions or billions of rows
Large file compaction
Shuffle optimization
Cluster autoscaling
Photon performance benchmarking
Partition pruning at scale
OPTIMIZE or ZORDER behavior
Cost-performance tuning
```

#### Rationale

The project is designed to be cost-aware and easy to reproduce.

Large-scale performance tuning can be added in future iterations.

### 11. Partitioning Limitation

The project uses limited partitioning.

The Gold fact table and daily summary use:

```text
order_date
```

#### Limitation

The project does not deeply explore partition design, file size optimization, or advanced layout tuning.

It does not implement:

```text
OPTIMIZE
ZORDER
Liquid clustering
Compaction strategy
Dynamic partition management
Large-scale partition pruning analysis
```

#### Rationale

The small dataset does not require advanced optimization.

The partitioning decision is included to demonstrate the concept without overengineering.

### 12. Data Quality Framework Limitation

The project implements explicit validation logic in PySpark.

#### Limitation

The project does not use an external data quality framework.

It does not use:

```text
Great Expectations
Deequ
Delta Live Tables expectations
Unity Catalog quality rules
Config-driven rule engines
```

#### Rationale

Explicit PySpark validation keeps the MVP readable and easy to defend.

The current implementation clearly shows the validation logic without hiding it behind a framework.

### 13. Rejected Records Limitation

The project writes invalid records to:

```text
silver_rejected_records
```

#### Limitation

The rejected records table captures the first detected rejection reason per record.

It does not capture multiple validation failures for the same record.

Example:

```text
A record may have an invalid parent order and an invalid quantity.
The MVP records only the first detected reason.
```

#### Rationale

The first-rejection pattern keeps the validation flow simple and readable.

A multi-error validation design can be added later.

### 14. SCD Type 2 Limitation

The customer dimension implements SCD Type 2.

Table:

```text
gold_dim_customer_scd2
```

#### Limitation

The SCD2 implementation does not cover all production dimension scenarios.

It does not implement:

```text
Late-arriving dimension changes
Same-timestamp conflict resolution
Hybrid Type 1 and Type 2 behavior
Soft deletes
Hard deletes
Source system priority rules
Reusable SCD2 framework
Warehouse-generated identity surrogate keys
```

#### Rationale

The project demonstrates the core SCD2 concept clearly:

```text
Detect changes → create versions → close prior versions → mark current record
```

That is sufficient for the MVP.

### 15. Product Dimension Limitation

The product dimension is implemented as a current-state dimension.

Table:

```text
gold_dim_product
```

#### Limitation

The product dimension does not implement SCD Type 2.

Product changes are demonstrated through Delta MERGE, not historical versioning.

#### Rationale

This keeps the project focused.

Customers demonstrate SCD Type 2.

Products demonstrate MERGE / upsert.

This separation avoids mixing too many patterns into one table.

### 16. MERGE Limitation

Delta MERGE is demonstrated using a small manually created source DataFrame.

Notebook:

```text
06_delta_merge_upsert_demo
```

#### Limitation

The MERGE source does not come from a production incremental feed.

It does not implement:

```text
CDC ingestion
Delete handling
Soft deletes
Late-arriving updates
Source-driven merge configuration
Reusable merge framework
Multi-table merge orchestration
```

#### Rationale

The goal is to demonstrate the MERGE pattern clearly:

```text
Existing product → update
New product → insert
```

The current implementation is intentionally small and focused.

Time travel is demonstrated on the product dimension.

### 29. Public Repository Limitation

The repository is public and intentionally avoids secrets.

#### Limitation

Certain environment-specific values are not fully reproducible by another user without creating their own Azure resources.

Examples:

```text
Storage account
Databricks workspace
Secret scope
Compute Spark configuration
ADLS containers
```

#### Rationale

This is expected.

The repository is designed to show implementation, architecture, and evidence, not to provide shared access to the original Azure environment.

- Databricks Jobs orchestration
- Unity Catalog tables and external locations
- Azure Key Vault-backed secret scope
- CI/CD with Databricks Asset Bundles
- Automated testing
- Config-driven data quality rules
- Job monitoring and alerting
- Power BI or Databricks SQL consumption layer
- Larger datasets
- Auto Loader or streaming ingestion
- Better incremental processing framework
- Table optimization strategy
- Operational metadata model

### 31. Summary

The known limitations in this document are intentional and aligned with the MVP scope.

The current project demonstrates:

- Azure Databricks execution
- PySpark transformations
- Delta Lake tables
- Bronze/Silver/Gold architecture
- Data quality validation
- Rejected records
- SCD Type 2
- Fact and summary modeling
- MERGE / upsert
- Time travel
- Validation reporting
- Secure credential handling
- Git-integrated execution
- Cost-aware development

The limitations do not weaken the project.

They clarify scope, prevent overclaiming, and define a credible path for future improvements.
